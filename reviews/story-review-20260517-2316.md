### TYPE 1 â€” Victim Identity Continuity (CRITICAL)

The story designates Eleanor Voss as the murder victim in Chapter 1, but she speaks, reacts, nods, and sits on sofas in every subsequent chapter including the aftermath. This is the most severe structural defect in the story.

| Ch | Issue |
|----|-------|
| 1  | Eleanor introduced as the lifeless body. |
| 2  | Eleanor speaks and gives testimony. |
| 3  | Eleanor nods and reacts emotionally. |
| 5  | Eleanor sits on the sofa. Beatrice asks Eleanor about "Eleanor's death." |
| 6  | Eleanor is present as a living suspect/witness. "Since Eleanor's tragic death" said while Eleanor watches. |
| 7  | Eleanor sits on the sofa and reacts emotionally. |
| 8  | Eleanor sits nearby reacting to accusations about her own death. |
| 9  | Eleanor is alive in the aftermath. "The time that had passed since Eleanor's tragic death" while Eleanor is in the room. |

**Root cause**: The `victimConfirmedDeadChapter` mechanism in `agent9-prose.ts` (~line 6678) detects victim death by scanning batch prose for co-occurrence of the victim name + death-language pattern. If the LLM writes the victim as alive in chapter 2+ before the detection fires, or if the detection fires late/not-at-all, the `â›” DEAD CHARACTER` guardrail block (~line 2541) is never injected. In this run, the guardrail either did not fire or was insufficient to stop the LLM from re-inserting Eleanor as alive.

**Agents requiring changes**: Agent 9 (prose), Agent 3 (CML/outline)

**Suggested fixes**:
1. **`agent9-prose.ts`** â€” Do not wait for `victimConfirmedDeadChapter` to be set by observation. The victim is always dead from before chapter 1. Inject the `â›” DEAD CHARACTER` block unconditionally for chapter â‰¥ 2 if `victimName` is resolved, regardless of whether the detection has fired.
2. **`agent9-prose.ts`** â€” Add an explicit rule to the chapter-type contract for `DISCOVERY` (chapter 1): "The victim is found dead. They do not speak, react, or interact at any point in this story."
3. **`agent9-run.ts`** â€” Add a post-generation linting pass: scan each chapter's paragraphs for the victim name in non-past-tense verb constructions and flag/retry if found.

### Code Reality: Two Critical Findings

**Finding 1 — The guard is conditional when it should not be.**

In `buildNSDBlock()` (~line 2541):
```typescript
if (state.victimConfirmedDeadChapter !== undefined) {
  // inject ⛔ DEAD CHARACTER block
}
```
`victimConfirmedDeadChapter` is set by scanning the *generated* prose for victim name + death-language co-occurrence. This means:
- If the LLM generates chapter 1 with weak death language, detection may not fire.
- If detection fires on chapter 3, chapters 2 and 3 had no guard.
- The victim is **always** dead from before chapter 1 — this is a structural story fact from the CML outline, not something to infer from generated text. The condition inverts causality.

**Finding 2 — The guard is buried mid-prompt (position 16 of 22).**

`buildPromptContextBlocks()` assembles context in this order:
`pronoun_accuracy [0] → character_consistency [1] → setting [2] → background [3] → world [4] → fair_play [5] → personality [6] → contracts [7] → physics [8] → era [9] → locations [10] → texture [11] → temporal [12] → locked_facts [13] → clues [14] → narrative_state [15] → continuity [16] → discriminating_test [17] → humour [18] → craft [19] → scene_grounding [20] → scoring [21]`

The dead character block lives inside `narrative_state` at position **15**. The generation instruction is appended after position 21. Research on "Lost in the Middle" (Liu et al., 2023) confirms that LLM attention weight for constraints decays toward the centre of long contexts. Position 15 of 22 is exactly where attention is weakest.

**Finding 3 — The victim appears in the active cast profile blocks.**

The victim's profile is passed to `character_personality` [6] and `character_consistency` [1] in the same format as living characters. The LLM receives a character profile for Eleanor Voss just like every other cast member, activating a deeply trained "cast member participates in scenes" prior. A distant block at position 15 then tells it to treat that same named character differently.

### The One Bug That Enables All Others

Before implementing any ideas, **one conditional must be removed**. Everything else is layered defence. The single line:

```typescript
if (state.victimConfirmedDeadChapter !== undefined) {
```

should become:

```typescript

```

(where `chapterIndex` is the current chapter number, already in scope). This makes the guard **structural, not observational**. The victim is dead before chapter 1. No inference needed.

### Golden Age Authenticity Lens

In an authentic 1930s Golden Age mystery, the victim being continuously and emphatically dead is not just a continuity rule — it is a genre convention with narrative weight. Christie, Sayers, and Allingham all rely on the *absence* of the victim as a presence: their effects, their diary, witnesses' memory of them. The mandatory memorial mention (Idea 7) actively serves this convention — it forces prose that references the victim elegiacally, which is exactly how Golden Age victims are handled. A murder victim who keeps showing up alive is not just a logic error; it destroys the elegiac tone that makes the genre work.

The **cast profile transformation** (Idea 8) also serves Golden Age authenticity: in a classical mystery, the victim is presented to the reader as a *case*, not a character — through others' testimony and through physical evidence. The LLM receiving a first-person-present-tense character profile for the victim is being given the wrong narrative register for the genre.

These two ideas together — cast profile as crime file, mandatory memorial reference — would make the generated prose feel authentically Golden Age even without the victim-alive bug, and they solve the bug as a structural side effect.

### Analysis: Which Three Changes Matter Most

**Change 1 â€” Pronoun block recency (position move + user message lock): HIGH EXPECTED IMPACT**

This is the architectural root cause fix. The pronoun table was being processed at position 0, thousands of tokens before generation. Moving the block to position 22 (last in developer context) and adding a compact per-character reminder in the user message directly before the scene outline means the pronoun constraints are now the last constraint the model encodes before outputting JSON. Expected result: a large reduction in first-attempt pronoun errors, especially for the majority-gender-default pattern (3:1 female-to-male cast producing `she` for Hale).

**Change 2 â€” Rule 10 (dialogue attribution name mandate): MEDIUM EXPECTED IMPACT**

Expected result: reduction in per-chapter repair pass invocations, especially for dialogue-heavy chapters.

**Change 3 â€” Exact sentence quoting in retry feedback: MEDIUM EXPECTED IMPACT**

Current retry feedback says `"found: her, she"` â€” the LLM cannot locate the specific sentences. With `extractPronounOffendingSentences()`, the retry message now quotes up to 3 specific sentences with wrong pronouns. The LLM gets surgical instructions rather than a general reminder.
